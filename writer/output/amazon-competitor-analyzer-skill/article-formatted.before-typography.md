> 摘要：介绍一个基于 SellerSprite MCP 的 Claude Skill：从评论和 Listing 中提取痛点，用三档评分输出三张表，直接给出产品开发优先级；也说明 20 条评论样本等硬限制。

很多竞品分析报告，信息很全，结论很轻。

价格、销量、评分、五点描述、A+ 内容都列上了，会议开完还是回到那句：“所以我们要做什么？”

**问题往往不在数据不够，而在分析顺序反了**：先看竞品有什么，再猜用户要什么。这样得到的是一份竞品说明书，不是产品决策。

`amazon-competitor-analyzer` 这个 Claude Skill 换了个顺序：先从评论里找用户在抱怨什么，再回到 Listing 看竞品有没有真的解决。最后只输出三张表，把“解决程度”和“开发优先级”放在一起。

## 竞品分析最常见的错：把“竞品有什么”当成“用户需要什么”

通用竞品分析习惯从竞品出发：销量多少、排名多少、卖点是什么、价格带在哪。这些信息当然有用，但它们回答的是“竞品长什么样”，不是“用户还有什么没被满足”。

这个 Skill 把出发点换成用户痛点。每一个痛点都必须有评论或 Listing 证据，不能靠“常识”推断，也不能因为“竞品少了一个功能”就认定用户需要它。

它和通用竞品分析的差别，可以压缩成一张小表：

| 维度 | 通用竞品分析 | 竞品解决方案分析 |
|---|---|---|
| 出发点 | 竞品数据 | 用户痛点 |
| 评价标准 | 销量、排名、价格 | 痛点解决程度 |
| 输出 | SWOT、battlecard | 痛点-解决方案矩阵 |
| 决策指向 | 竞争定位 | 产品开发优先级 |

所以它不输出 SWOT。不是 SWOT 没用，而是这份 Skill 只服务一个决策：下一版产品先做什么。

## 只回答一个问题：这项痛点，竞品解决到什么程度

评分只有三档，定义得很窄：

- **已解决得很好**：竞品通过功能、设计、服务或内容充分满足痛点，评论里鲜有负面反馈。
- **解决了一半**：有对应方案，但存在体验瑕疵、覆盖不全或条件限制，用户仍有抱怨。
- **基本没解决**：没有对应方案，或者方案效果差，用户反复抱怨。

三档分别对应三种开发判断：不作为核心方向、体验升级机会、重点未满足需求机会。

这里最容易出错的一步，是把 Listing 的自述当成结论。标题写了 “12-hour battery”，不等于续航问题解决了；五点描述写了 “noise cancellation”，也不等于用户认可。Skill 要求主图和详情页卖点与评论双向验证，同一痛点有多个方案时，取最高评分作为竞品当前水平。

还有一条防主观臆测的规则：缺少某个功能，不自动等于用户痛点。除非评论里有人明确抱怨，否则不能把它写进痛点清单。

## 三张表，分别对应三个决策

第一张是《痛点-竞品解决矩阵表》。行是用户痛点，列是竞品已经提供的解决方案，单元格填评分和一句话证据。

它的读法不是“填满”，而是“找空格”：哪一行所有方案都是“基本没解决”，那就是市场级机会；哪一行只有个别竞品没解决，那是单点超越机会。

第二张是《竞品解决方案拆解表》。每个方案占一行，写清楚来源位置、功能、目标痛点、用户价值、证据摘要和当前缺口。

这张表解决的是“为什么没解决”。同样是续航，有的问题是电池容量不够，有的是标称虚高，有的是充电速度拖后腿。拆开之后，行动才会具体到“升级到 1200mAh 并增加快充”，而不是一句“改进续航”。

第三张是《竞品解决方案分析表》。按评分从低到高排序，每组给出建议行动。

它相当于把前两张表的结论收束成待办清单：先做“基本没解决”的，再做“解决了一半”的，最后决定“已解决得很好”的要不要跟进。

## 评分不是打分，是走一棵决策树

为了避免凭感觉给分，Skill 把评分过程写成了判断顺序：

1. 竞品有没有明确方案？没有，就是“基本没解决”。
2. 有方案，评论里是否至少有两条明确负面反馈？有，就是“解决了一半”。
3. 没有明显负面，再看正面或中性反馈是否达到约七成。达到，才算“已解决得很好”。

这套规则不完美，但它强迫每个评分都回到证据。尤其重要的是“已解决得很好”的要求：需要正面证据占主导，而不是“没看到差评”就默认过关。

## 数据从哪来，哪些限制必须先知道

数据来自 SellerSprite MCP。Skill 主要调用四个工具：

- `asin_detail`：标题、品牌、价格、评分、销量、主图、卖点、变体等 Listing 信息。
- `review`：评论内容、星级和日期，用来提取痛点。
- `keepa_info`：价格和 BSR 趋势，可选。
- `competitor_lookup`：输入关键词时，先找销量最高的几个 ASIN。

有三个限制，跑之前最好先接受：

**第一，评论每次最多 20 条。** 所有基于评论的结论都必须标注“基于最近 20 条样本”。这意味着它适合发现线索，不适合证明普遍性。

**第二，字段名和网页 API 不完全一样。** 评论内容是 `content` 而不是 `body`，销量是 `units` 而不是 `totalUnits`，销售额是 `revenue` 而不是 `totalAmount`。用错字段，对应的数据就会是空的。

**第三，参数模式分两种。** `asin_detail`、`review`、`keepa_info` 用扁平参数；`competitor_lookup` 和 `traffic_keyword` 要用 `{"request": {...}}` 嵌套。混用会直接报错。

另外，评论样本可能偏向近期，标题和描述里的 HTML 实体也要先解码，否则 `&amp;` 会原样写进报告。

## 安装与运行

先准备 SellerSprite 账号和 secret key，然后在项目根目录创建 `.mcp.json`：

```json
{
  "mcpServers": {
    "sellersprite": {
      "url": "https://mcp.sellersprite.com/mcp",
      "headers": {
        "secret-key": "你的密钥"
      }
    }
  }
}
```

密钥放在 `headers` 里，不要拼到 URL 查询参数上。这是这份 Skill 文档里特别强调的配置差异。

然后把 Skill 放到 `.claude/skills/amazon-competitor-analyzer/`，或者软链到全局 skills 目录。装好后可以直接输入：

```
/competitor-solution-analysis B0XXXXXX
/analyze-competitor-solution https://www.amazon.com/dp/B0XXXXXX
/competitor-solution-analysis wireless lavalier microphone
```

第三种会先取销量最高的三个 ASIN，分别分析，再给一张横向对比表。

需要说明的是，Skill 文档里的示例输出明确写着“仅展示格式，不代表真实数据”。它的作用是让你知道三张表长什么样，不是让你引用其中的销量、评分或评论结论。

## 这套方法的边界

最重要的一条：**20 条评论不是市场调研。**

它能帮你快速形成假设，但不能证明某个痛点在整个市场普遍存在。评论还可能集中在近期，或者被少数激烈用户主导。正确用法是把它当作初筛：先找出“值得进一步验证”的痛点，再用更多评论、用户访谈或退货原因去确认。

第二条：**评分是编辑判断，不是统计结论。** 三档评分依赖证据摘要和判断规则，不同人看同一批评论，仍可能给出不同分数。它的价值在于把判断过程摊开，而不是制造精确感。

第三条：**“已解决得很好”不等于没有机会。** 竞品可能功能上解决了，但表达、服务、配件组合或某个细分场景仍有空间。矩阵表告诉你不要把它当核心开发方向，不意味着不能做差异化。

如果你需要的是市场规模测算、成本可行性或供应链判断，这个 Skill 不负责这些。它只回答一个更窄的问题：从用户抱怨和竞品方案对照来看，下一版产品应该先动哪里。

## 下次看竞品，先问差评在抱怨什么

**竞品分析最容易产生的错觉，是数据越多，判断越准。**

实际情况常常相反：数据越多，越容易停在描述层。真正推进决策的，往往是一张不大的表：左边是用户反复抱怨的几件事，右边是竞品到底解决到什么程度。

如果你手头正有一个 ASIN，可以先做一个小动作：把最近 20 条评论按星级分组，只聚类差评和中评里的高频抱怨，得到 4 到 7 个痛点；再回到 Listing，为每个痛点找一个对应方案，找不到就标“基本没解决”。

这一步不需要完整跑完 Skill，也能让你在下一次选品会前，多一个可讨论的判断，而不是又一份参数清单。
