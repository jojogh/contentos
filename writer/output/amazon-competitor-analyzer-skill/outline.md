# 提纲

## 标题方向

主标题：一个 ASIN，三张表：把亚马逊竞品分析从“参数罗列”变成“机会判断”
读者承诺：看完知道这个 Skill 怎么把评论和 Listing 变成产品开发优先级，也知道它的数据边界在哪。

## 开头钩子

从常见失败场景切入：竞品报告写满价格、销量、评分和卖点，会议结束后仍然没人知道该做什么。材料来源：编辑观察，不虚构具体人物或事件。

## 主章节

### 1. 竞品分析最常见的错：把“竞品有什么”当成“用户需要什么”
- 服务主张：C1
- 读者问题：为什么数据很多，结论很少？
- 推进：从数据罗列转向痛点解决程度

### 2. 这个 Skill 只回答一个问题：每项痛点，竞品到底解决了没有
- 服务主张：C1、C4
- 证据：三档评分定义、双向验证原则
- 读者问题：怎么避免被 Listing 营销话术骗？

### 3. 三张表，分别对应三个决策
- 服务主张：C5
- 证据：矩阵表、拆解表、分析表的字段和用途
- 读者问题：输出长什么样，怎么读？

### 4. 数据从哪来，以及三个容易踩的坑
- 服务主张：C2、C3、C8
- 证据：MCP 工具、20 条样本、字段映射、参数模式
- 读者问题：跑之前要知道什么？

### 5. 安装与运行：一条命令背后的配置
- 服务主张：C6
- 证据：`.mcp.json` 格式、命令示例
- 读者问题：怎么开始用？

## 反方、边界或使用条件

- 服务主张：C9
- 反方：20 条样本、主观评分、近期评论偏差
- 回应：把评分定位为初筛判断；列出需要二次验证的环节

## 结尾

回到开头：下次看竞品，不要先问“它卖得怎么样”，先问“它的差评在抱怨什么，Listing 有没有真的解决”。给一个当天可执行的动作：挑一个 ASIN，先聚类 20 条评论，再做矩阵。
