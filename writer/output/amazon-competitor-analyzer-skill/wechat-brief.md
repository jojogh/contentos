# 公众号文章任务书

- 账号/栏目：未提供（按 AI × 电商工具实操栏目处理）
- 目标读者：做 Amazon 选品、产品开发和运营的人；以及想用 Claude Code 搭建电商分析工作流的人
- 阅读场景：在选品会前、看竞品 Listing 时，想快速判断“哪些痛点还没被解决”
- 读者真正问题：竞品分析报告写了很多数据，为什么还是不知道怎么定产品方向？
- 读后交付：理解这个 Skill 的分析逻辑、三张表的用法、评分标准，以及数据和样本的硬限制
- 核心判断：竞品分析的价值不在收集更多数据，而在判断每项用户痛点“到底解决了没有”；只有把 Listing 方案和评论证据放在同一张表里对照，才能产出可执行的产品机会
- 新增价值：给出一个可运行的 Skill 设计，包括数据源、评分决策树、三张表结构，以及评论样本、字段映射等具体陷阱
- 文章类型：痛点解法 / 工具介绍
- 目标长度：2000-2800 个中文字符
- CTA：拿一个正在看的 ASIN，先跑评论聚类，再对照 Listing 找方案，最后看矩阵里哪些格子是“基本没解决”

## 适用边界

- 适用：Amazon 竞品初筛、新品开发方向判断、产品迭代找差异点、选品阶段判断未满足需求
- 不适用：需要统计显著性的市场研究、需要真实用户访谈验证的决策、供应链和成本可行性判断
- 最强反方：20 条评论样本太小，评分带主观性，容易把个别抱怨放大成市场机会
- 本文如何回应：明确把评分定义为“编辑判断”而非统计结论，要求每个评分附证据，并在文中列出样本限制和验证下一步

- 允许写成第一人称的范围：对分析逻辑和产品判断的第一人称观点；不虚构测试过程、客户、对话或真实 ASIN 结果

## 需要证明的主张

1. 这个 Skill 以用户痛点为锚点，而不是以竞品数据为起点
2. 它通过 Listing 卖点与评论证据双向验证，给出三档评分
3. 最终输出三张表，分别回答“解决程度”“方案怎么拆”“先做什么”
4. 评论工具每次最多返回 20 条，所有结论都带样本限制
5. 安装需要 SellerSprite MCP 的 secret-key，并按指定 JSON 格式配置
6. 这套方法适合初筛和方向判断，不适合替代统计研究或真实用户验证
