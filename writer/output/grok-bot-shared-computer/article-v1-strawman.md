# Grok Bot 不给每个 AI 配电脑，给每个账号配一台

> 摘要：Grok Bot 的常见介绍是「每个 agent 一台云 VM」，官方文档说的正相反：一个账号只有一台云电脑，bot 之间只分屏幕、不分权限。这决定了它该怎么用。

8 月 20 日，@monokern 发了一篇 Grok Bot 的搭建指南。它给了一个很顺的前提：每个 agent 拥有一台专属云 VM，带持久浏览器、终端、文件系统和后台运行器，所以你合上笔记本它还在干活。

这个前提符合所有人对「AI 同事」的想象——一个同事一张工位。

但它和官方文档对不上。

xAI 的 Grok Bot 文档里有这么一句："Every Bot on your account uses the same computer."。紧接着还有一句更不留余地的："The computer is assigned to your user account, not an individual Bot."

一个账号，一台电脑。不是每个 bot 一台。

这不是细枝末节。它决定了你该建几个 bot、能把什么放进去、以及哪些任务根本不该交给它。

## 「屏幕」是工位，不是隔断

文档里确实给了一个听着像隔离的词：screen。"Each Bot gets its own screen on the shared computer."

每只 bot 在共享电脑上分到一块自己的屏幕。读到这儿很容易松一口气——原来还是分开的。

下一句把这个幻觉戳破了："The screens are separate work surfaces, not separate security boundaries."

**工作区，不是安全边界。**

共享到什么程度，文档列得很清楚：文件对所有 bot 可见；命令行凭据是共享的；浏览器 cookie 和登录态是共享的；连装好的连接器也是账号级的。持久文件放在 `/workspace`，那也是同一个目录。

然后是这句我认为最该抄进任何一份内部规范的话：

> "Do not place a credential or file on it if another Bot on your account should not be able to use it."

如果你不打算让账号里另一只 bot 用到某个凭据或文件，就不要把它放上去。

注意这句话的性质。它不是「请小心一点」，而是在说：这套系统里不存在「只给这一只 bot 看」这种东西。

## 多一只 bot，就多一个能读你全部文件的人

有三个后果，都是这句话推出来的。

**第一，bot 数量不是免费的。** 每多一只，就多一个能读到 `/workspace` 全部内容的主体。在没想清楚之前先加人，等于开一扇只会越开越大的门。

**第二，「让它自己登录一下」是个错误的问题。** 这套设计的本意就是登录一次、全账号通用。所以真正该问的不是「怎么让这只 bot 登录」，而是「登录之后，谁还能用这个身份」。

**第三，并发是有上限的。** 一块屏幕同一时间只处理一个 computer-use 任务。想并行就得开新 bot，而新 bot 又是同一个文件系统、同一套凭据。

第三条值得单独说。它意味着：**你能买到的并行度，和你要承担的权限暴露面积，是同一个旋钮。** 想把活干快一点，就得把门再开大一点。

这个耦合关系不是我加的，是把上面那几句话放在一起看的结果。但它有一个很实际的推论：如果你正打算靠加 bot 来提速，先想清楚你能接受多大的门。

## 同一套技术，两种相反的答案

Meta 的 Muse 走的是同一条「给 agent 一台持久云电脑」的技术路线，但把边界放在了完全不同的位置。

按 Forkast 9 月 13 日的对比，Grok Bot 是账号级隔离：Firecracker 微虚机隔开的是不同用户，同一账号内部的 bot 共享同一个运行时。

Muse 则给每个用户独立的 Linux VM，再用一个叫 Sentinel 的宿主侧代理，充当所有连接器操作和网络出口的唯一权限方。凭据存在运行时之外，在网络边界处即时注入——按他们的描述，agent 从头到尾见不到真实 token。

一个把 agent 当成用户的代理，用共享状态换协作顺畅；一个把 agent 当成不可信进程，用权限刚性换可控。

没有谁更先进。但你要知道自己在买哪一条。

需要说明的是，Muse 这部分我只看得到 Forkast 的转述，没打开 Meta 的原始文档，所以细节按二手资料对待。

## 那套「总参谋长 + 专员」还值得抄吗

回到开头那篇指南。它给的设计是一套组织架构：一个总参谋长负责拆解目标、分派任务，下面挂研究、文案、设计、运营、财务几个专员；每只 bot 的描述文件就是组织架构图，总参谋长靠读这些描述决定派谁。

这套方法不难用，但顺序反了。

在一个共享文件系统的前提下，先建组织、后想权限，等于先装修再决定哪面墙承重。合理顺序是倒过来的：**先确定哪些信息绝对不能互相看见。**

如果答案是「没有」，那这些活一只 bot 就能干完，多建的只是管理成本。

如果答案是「有」，那这套组织架构根本不该建在同一个账号里——你需要的是分开的账号，或者干脆分开的产品。

## 更值得抄的两个做法

指南里另外两个做法我认为值得抄，而且不依赖具体产品。

一是**教一次**。录一遍你手工操作的流程，系统分析 DOM 事件和鼠标动作，生成一份可编辑的 Skill File，并带上限流和意外弹窗的护栏。这比让模型自己猜界面怎么点要稳得多。

二是**可逆性矩阵**。可逆的事——抓数据、写草稿、整理文件——让它自己跑；不可逆的事——发消息、付款、改生产环境、发布——必须人过一遍。作者的建议是在 bot 的章程末尾写死一句边界条款，大意是「未经人工复核，你绝不能点发送」。

这两条合起来其实是同一个思路：把不确定性留在可逆的一侧。

顺带说一句价格。Grok Bot 没有单独卖，是跟订阅档位绑定的。具体是哪几档、各多少钱，我没能核实——官方定价页返回 403，搜到的数字互相矛盾，有的把同一个档位说成两个价。所以这里不给数字，只给一个更实用的动作：先查你现有的订阅里有没有包含，再考虑要不要升。

## 反方：共享恰恰是它想卖的东西

有一个反对意见值得认真对待。

共享状态不是疏忽，是产品取向。现实里绝大多数工作流本来就要跨工具——同一份客户资料、同一套报价、同一个登录态。如果每只 bot 都被硬隔开，你会把大量时间花在同步数据上，而不是干活。这套设计假设你信任自己的 bot，并愿意为此换来顺畅。

所以真正的问题不是「共享好不好」，而是「什么条件下它不成立」。

我给三个条件：

- 账号里同时存在处理客户数据的任务和产出公开内容的任务
- 有外部人员（外包、实习生、临时协作者）能给你的 bot 下指令
- 你要把涉及真实资金的支付凭据交给它

在这三种情况下，共享文件系统不是便利，而是一个你用不上、但会一直存在的暴露面。

## 结尾：先做减法

如果你正准备开第一个 Grok Bot，我建议的第一个动作不是搭一支五人团队，而是做一件更小的事：

打开官方文档那一页，把你打算放进 `/workspace` 的东西列一遍，然后对着每一行问一次——如果账号里另一只 bot 看到了它，会怎样。

想清楚这个，再决定你要雇几个同事。

接下来我会看两个信号。一是 xAI 会不会给 bot 之间加上权限控制，那会直接推翻上面第三条结论。二是企业版那套逐项审批和审计能力会不会下放到个人档位——如果下放了，说明他们自己也认为这里的边界需要补。
