摘要：Grok Bot 给每个账号配一台常驻云电脑，bot 之间只分屏幕、不分权限。本文用一篇爆款指南和官方文档互相对照，说清它能干什么、以及什么东西不该放进去。

8 月 20 日，@monokern 发了一篇 Grok Bot 架构指南。到 10 月中旬，这篇长文被浏览了 125 万次，收藏 1030 次。

它给的承诺很直接：你合上笔记本，agent 团队继续在数据中心里干活。

指南里第一批被转发的句子，是关于机器的那句：

"each Grok Bot agent receives its own dedicated cloud virtual machine - complete with a persistent web browser, terminal, file system, and background process runner."

每个 agent 一台专属云虚拟机，带持久浏览器、终端、文件系统和后台进程运行器。

这句话解释了很多事：为什么它们能 24 小时不睡，为什么登录一次就够，为什么一支团队听起来像同事。

但它不是这篇指南里唯一关于机器的一句话。

同一篇文章，两种机器

二十段之后，指南在讲登录交接时又写了一句：

"Because all bots on your account share the underlying cloud environment, authenticating a service once makes that active session available to your entire agent roster."

因为账号上的所有 bot 共享底层云环境，所以一个服务认证一次，整个 agent 团队就都能用。

前一句说「专属虚拟机」，后一句说「共享底层环境」。两句挨着同一篇文章，都在讲同一台机器。

这不是笔误，甚至不是作者的疏忽——后一句才是他推荐「认证一次、全员可用」这套做法的依据。真正的问题是，两句不可能同时为真。

官方文档站在后一句那边

xAI 的 Grok Bot 文档写得没有余地：

"Every Bot on your account uses the same computer."
"The computer is assigned to your user account, not an individual Bot."

一个账号，一台电脑。分配对象是用户，不是某只 bot。

文档确实给了一个听着像隔离的词：screen。

"Each Bot gets its own screen on the shared computer."

每只 bot 在共享电脑上分到一块自己的屏幕。读到这儿很容易松口气——原来还是分开的。

下一句把这个幻觉戳破了：

"The screens are separate work surfaces, not separate security boundaries."

工作区，不是安全边界。

共享到什么程度，文档列得很清楚：文件对所有 bot 可见；命令行凭据共享；浏览器 cookie 和登录态共享；连装好的连接器也是账号级的。持久文件放在 /workspace，那也是同一个目录。

然后是这句：

"Do not place a credential or file on it if another Bot on your account should not be able to use it."

如果你不打算让账号里另一只 bot 用到某个凭据或文件，就不要把它放上去。

注意这句话的性质。它不是「请小心一点」，而是在说：这套系统里不存在「只给这一只 bot 看」这种东西。

那「专属」到底指什么

隔离发生在账号这一层。不同账号之间是分开的；同一个账号内部，所有 bot 落在同一个运行时里。

所以指南那句「dedicated」的准确含义，是每只 bot 有自己的屏幕、浏览器标签和任务队列，不会互相打断。

仅此而已。它没有承诺独立的文件系统，也没有承诺独立的凭据。它读起来像在说后者。

这个区别决定了你该怎么用它。

三个用法约束

第一，bot 数量不是免费的。 每多一只，就多一个能读到 /workspace 全部内容的主体。在没想清楚之前先加人，等于开一扇只会越开越大的门。

第二，「让它自己登录一下」问错了。 这套设计的本意就是登录一次、全账号通用。真正该问的不是「怎么让这只 bot 登录」，而是「登录之后，还有谁能用这个身份」。

第三，并发有上限，而且和暴露面是同一个旋钮。 一块屏幕同一时间只处理一个 computer-use 任务。想并行就得开新 bot，而新 bot 又是同一个文件系统、同一套凭据。

第三条值得单独说。你能买到的并行度，和你要承担的权限面积，是同一个旋钮。 想把活干快一点，就得把门再开大一点。

这条不是官方表述，是把上面几句话放在一起的推论。但它有个很实际的用法：如果你正打算靠加 bot 来提速，先想清楚自己能接受多大的门。

指南搭的那支团队

放下机器的问题，先看这指南到底教人搭了什么。

它给的是一套小型组织：一个总参谋长（Klaus）接住所有请求，下面挂研究员（Mara）、文案（Cole）、设计师（Rina）、运营（Vince）。

分工方式不是靠你手动转派。指南写道，每只 bot 的描述文件就是它在组织架构图里的那一行，Klaus 收到需求后会扫描所有 bot 的描述，谁写着「负责市场调研、线索发现和竞品抓取」，调研任务就自动转给谁。

这解释了一个容易忽略的点：那份描述不只是给人看的说明书，它是派工依据。

正文列了五个核心角色。不过作者放的架构图里，侧边栏列的是六只 bot，多出来的那个是财务（Jonathan，管预算和审计）——五和六的差别不大，但它提醒你：这类指南的正文和图经常不是同一版。

对没有原生集成的平台（YouTube、Reddit、LinkedIn 之类），指南的做法是接一个 Composio 作为总插件，再往共享知识库里写一条规则，让所有 bot 都知道扩展工具从那儿走。

至于定位，作者说得很清楚：Grok Bot 不是 Claude Code 的替代品，而是互补层——复杂的 TypeScript 重构、架构设计、数据库迁移留在本地做，跑日常例行任务的才放到云上那支团队。

指南里值得抄的三件事

尽管关于机器的描述前后打架，这篇指南有三块内容我认为该保留。

一是交互式会话交接。 bot 撞到登录墙或两步验证时暂停，把「Agent Computer」的屏幕请求推给你；你在实时云浏览器里自己输密码、自己过验证，点完成；bot 拿到的是一张已认证的会话凭证，密码从头到尾没进过模型上下文。

这比在聊天框里粘 API key 好得多。也要看清它成立的前提：指南自己说了，认证一次，全账号可用。

二是 /workspace 持久化。 指南指出云虚拟机定期重建镜像，/home 下的依赖、/usr/local、全局 apt 包、手动装的 CLI 工具在重建后全部消失，只有 /workspace 保证存活。所以技能文件、二进制和状态数据都应该放进 /workspace/skills/ 和 /workspace/state/，并在技能文件头部加一段自愈启动脚本，重建后自动补依赖。

它顺带提到一件容易被忽略的事：Grok Bot 给的是免密 root（sudo (ALL) NOPASSWD: ALL），所以 bot 能自己修环境，不需要人工介入。

这句话在指南里是能力描述。放到前面那个共享前提下，它同时是风险描述——账号级共享的东西，包括 root。

三是可逆性矩阵。 可逆的事让它自己跑，不可逆的事必须人过一遍。指南建议把边界写死在每只 bot 的角色描述末尾：

"YOU MUST NEVER click 'Send' or transmit an external email without explicit human review and approval in the chat thread."

这里还有个细节值得记：在 Grok Bot 里，bot 的描述文件就是组织架构图的一行。总参谋长靠读下属的描述来决定派谁干活。所以描述不只是说明书，它是派工依据——写进去的权限边界是真的会生效的。

教一次（Teach-a-Task） 也在这一组里：录一遍手工流程，系统分析 DOM 事件和鼠标动作，生成可复用的 Skill File，再补上重试和校验护栏。图里那个例子的护栏是「最多重试三次、退避等待」「只导出 CSV」「文件为空即失败」。

反方：共享恰恰是它想卖的东西

有一个反对意见值得认真对待。

共享状态不是疏忽，是产品取向。现实里绝大多数工作流本来就要跨工具——同一份客户资料、同一套报价、同一个登录态。如果每只 bot 都被硬隔开，你会把大量时间花在同步数据上，而不是干活。这套设计假设你信任自己的 bot，并愿意为此换来顺畅。

所以真正的问题不是「共享好不好」，而是「什么条件下它不成立」。

我给三个条件：

  • • 账号里同时存在处理客户数据的任务和产出公开内容的任务
  • • 有外部人员（外包、实习生、临时协作者）能给你的 bot 下指令
  • • 你要把涉及真实资金的支付凭据交给它

在这三种情况下，共享文件系统不是便利，而是一个你用不上、但会一直存在的暴露面。

结尾：先做减法

如果你正准备开第一个 Grok Bot，第一个动作我建议不是照指南搭一支五人团队。

打开官方文档那一页，把你打算放进 /workspace 的东西列一遍，然后对着每一行问一次——如果账号里另一只 bot 看到了它，会怎样。

想清楚这个，再决定你要雇几个同事。

接下来我会看两个信号。一是 xAI 会不会在 bot 之间加权限控制，那会直接推翻上面那个「并发与暴露同源」的推论。二是企业版那套逐项审批和审计会不会下放到个人档位——如果下放了，说明他们自己也认为这里的边界需要补。
